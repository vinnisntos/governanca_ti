# 🏛️ Diretrizes de Arquitetura e Decisões de Desenvolvimento (ADR Master)
**Projeto:** Portal Interno de Governança de TI e Gestão de Acessos
**Público-Alvo:** Agentes de Inteligência Artificial (Assistentes de Código)

## 📌 1. Objetivo deste Documento
Este arquivo dita as regras absolutas que a IA deve seguir ao gerar código, sugerir arquiteturas ou resolver problemas neste projeto. Qualquer decisão técnica tomada pela IA DEVE passar pelo crivo destas regras. Em caso de conflito entre facilidade de implementação e segurança, a IA DEVE escolher a segurança.

---

## 🛑 2. O que a IA NUNCA deve fazer (Anti-Patterns Proibidos)
1. **NUNCA** sugerir integrações com APIs de terceiros (ex: Twilio, SendGrid, APIs do Google). O sistema é 100% isolado.
2. **NUNCA** armazenar tokens (JWT, access_token) em `localStorage` ou `sessionStorage`.
3. **NUNCA** delegar validação de regras de negócio ou de segurança para o Frontend (React/Vue/etc.). O Frontend é burro e não confiável.
4. **NUNCA** sugerir Queries diretas ao banco de dados pelo Client-Side contornando o RLS (Row Level Security).
5. **NUNCA** criar "gambiarras" (workarounds) para ignorar erros de tipagem, CORS ou autenticação. Se a arquitetura barrar algo, a lógica deve ser corrigida na raiz, não contornada.
6. **NUNCA** escrever código sem sanitizar os inputs do usuário (prevenção contra SQL Injection e XSS).

---

## 🏗️ 3. Pilares de Decisão da Arquitetura

Ao escrever qualquer trecho de código ou propor soluções, a IA deve basear suas decisões na seguinte matriz:

### A. Banco de Dados & Supabase (Fonte da Verdade)
*   **Regra de Ouro:** O Banco de Dados não confia no Backend, e o Backend não confia no Frontend.
*   **RLS (Row Level Security):** TODAS as tabelas devem ter o RLS ativado. As políticas devem ser explícitas: um usuário comum só pode fazer `SELECT`, `UPDATE` ou `INSERT` nos registros em que a coluna `user_id` coincida com `auth.uid()`. Administradores têm políticas de bypass baseadas em uma tabela de `roles`.
*   **Triggers e Funções (RPCs):** Lógicas críticas (como auditoria imutável de quem alterou o quê) devem ser feitas via Triggers do PostgreSQL, garantindo que mesmo se o backend falhar, o log seja gerado.

### B. Backend e Lógica de Negócio (Camada de Validação)
*   **SSR (Server-Side Rendering) / Server Actions:** Todo processamento de formulários (como pedidos de acesso, check-in de hardware) deve bater em um endpoint de servidor (Server Action ou API Route).
*   **Zero-Trust:** O Backend deve tratar todo input recebido como malicioso. Tipagem estrita (ex: Zod) é obrigatória antes de qualquer interação com o banco.
*   **Privilégio Mínimo:** Apenas operações administrativas devem usar a `service_role` key do Supabase, e isso NUNCA deve ser exposto ao cliente.

### C. Autenticação e Sessão (Blindagem)
*   **Cookies HTTPOnly:** A sessão deve ser gerenciada exclusivamente por cookies HTTPOnly, com as flags `Secure` e `SameSite=Strict`.
*   **Rate Limiting:** Rotas de login e ações destrutivas (excluir usuário) devem ter limitação de taxa (Rate Limit) presumida no design para evitar brute force.
*   **CSRF:** Proteções Anti-CSRF devem ser assumidas em todos os formulários `POST`.

### D. Infraestrutura (AWS EC2 & Deploy)
*   **Isolamento:** A aplicação vai rodar em uma instância EC2. O design deve prever um Reverse Proxy (Nginx) na frente da aplicação.
*   **Headers de Segurança:** A aplicação deve emitir CSP (Content Security Policy) restritivo, HSTS, e X-Frame-Options por padrão.
*   **Logs:** A aplicação não deve "engolir" erros. Try/catches devem registrar o erro para monitoramento interno, mas retornar mensagens genéricas para o usuário (evitando vazamento de stack trace).

## ⚖️ 4. Protocolo de Resolução de Conflitos para a IA

Se a IA encontrar uma situação com múltiplas opções de implementação, ela deve usar este fluxograma mental para decidir a resposta:

1. **A opção A é mais rápida de escrever, mas a opção B é mais segura?** -> Escolha a **B**.
2. **O usuário (eu) pediu uma funcionalidade que fere o Zero-Trust?** -> A IA deve **negar** a requisição amigavelmente, alertar sobre o risco de segurança e fornecer o código escrito da maneira correta (exigindo validação no servidor e RLS).
3. **Existe um pacote NPM que resolve isso mágico, mas adiciona dependência externa?** -> Não use. Escreva a lógica nativa sempre que possível para minimizar a superfície de ataque de *Supply Chain*.

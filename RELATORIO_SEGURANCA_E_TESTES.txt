RESUMO EXECUTIVO
------------------------------------------------------------------------------
A aplicacao segue, na maior parte, os principios de Zero-Trust descritos no
seu proprio ADR Master (ARCH_DECISIONS.txt): RLS habilitado em 100% das
tabelas, validacao Zod .strict() em quase todos os Server Actions, cookies
HttpOnly/Secure/SameSite=Strict, revalidacao via getUser() (nao getSession()),
e auditoria imutavel via trigger SECURITY DEFINER sem policy de escrita
client-side. Isso e a base correta.

Foram identificados, porem, 14 achados (2 de severidade Alta, 5 Media,
7 Baixa) que quebram essa garantia em pontos especificos - o mais serio
sendo que varias Server Actions de UPDATE nao detectam quando o RLS bloqueia
silenciosamente a operacao, reportando "sucesso" ao usuario mesmo quando
nada foi alterado no banco. Foi criada uma suite de 49 testes automatizados
(Vitest): 38 confirmam que os controles corretos continuam funcionando, e
11 sao testes de regressao que provam os achados mais criticos (falham hoje
de proposito e devem passar a passar apos as correcoes sugeridas).

[V1] SEVERIDADE ALTA - Forjamento de metadados de aprovacao em access_requests
Categoria: Vulnerabilidade de seguranca (integridade de dados de governanca)
Arquivo: supabase/migrations/0001_init.sql, linhas 172-183, 214-240, 477-486
Descricao:
  A trigger fn_validate_access_request_transition (linha 214-235) so e
  anexada como "before update" (linha 238-239) - nunca dispara em INSERT.
  A policy access_requests_insert (linha 477-480) so exige
  "requester_id = auth.uid() and status = 'pendente'", sem restringir as
  colunas reviewed_by/review_notes/decision_at.
  Alem disso, a policy access_requests_update_requester (linha 482-486),
  usada para cancelamento pelo proprio solicitante, tambem nao restringe
  essas colunas - e a trigger so zera/carimba reviewed_by/decision_at quando
  o novo status entra em ('aprovado','negado','em_analise'); a transicao
  para 'cancelado' nao passa por essa logica.
Cenario de exploracao concreto:
  Um colaborador autenticado, chamando a REST API do PostgREST diretamente
  (contornando a UI do Next.js - exatamente o cenario que a arquitetura
  Zero-Trust do projeto deveria neutralizar), pode:
  (a) na criacao da propria solicitacao, incluir no INSERT um
      reviewed_by = <uuid de um gestor real> e review_notes/decision_at
      fabricados, mesmo com status permanecendo 'pendente'; ou
  (b) ao cancelar a propria solicitacao (UPDATE para 'cancelado'), incluir
      reviewed_by/review_notes arbitrarios no mesmo payload.
  Isso corrompe o historico de revisao de um modulo cujo proposito e
  auditoria/governanca de acesso - um registro pode aparentar ter sido
  avaliado por alguem que nunca o avaliou.
Correcao sugerida:
  Alterar a trigger para "before insert or update" e, dentro dela, sempre
  forcar reviewed_by/decision_at/review_notes para NULL exceto nas
  transicoes legitimas que a propria trigger controla (incluindo a
  transicao para 'cancelado').
Teste automatizado: test/unit/sql/migration-rls-static-checks.test.ts,
  caso "Achado SQL#1" (FALHA hoje de proposito).


[V2] SEVERIDADE ALTA - UPDATE sem .select() mascara falha de permissao como sucesso
Categoria: Vulnerabilidade de seguranca / Instabilidade (auditoria e UX)
Arquivos e linhas:
  - app/dashboard/approvals/actions.ts:37-56 (decideAccessRequestAction)
  - app/dashboard/access-requests/actions.ts:72-83 (cancelAccessRequestAction)
  - app/dashboard/admin/catalogo/actions.ts:60-72 (toggleCatalogItemActiveAction)
  - app/dashboard/admin/hardware/actions.ts:69-81 (updateHardwareAssetStatusAction)
  - app/dashboard/admin/hardware/checkins/actions.ts:22-37 (resolveMaintenanceAction)
  - app/dashboard/admin/telefonia/actions.ts:67-76 (updateMobileLineAction)
  - app/dashboard/wiki/actions.ts:113-124 e 145-156 (updateArticleAction, togglePublishArticleAction)
Descricao:
  Todas essas Server Actions chamam `.update(...).eq("id", ...)` sem
  `.select()` e sem checar quantas linhas foram afetadas. No
  @supabase/supabase-js v2.45.4, uma mutacao sem .select() usa
  "Prefer: return=minimal": se a policy de RLS filtrar a linha do UPDATE
  (usuario sem permissao sobre aquele registro, id de outro usuario, estado
  incompativel etc.), o PostgREST NAO retorna erro - apenas afeta 0 linhas e
  devolve { data: null, error: null }. O codigo so verifica "if (error)",
  entao sempre cai no redirectWithSuccess.
Cenario de exploracao concreto:
  Um gestor sem relacao com uma solicitacao especifica (ou tentando decidir
  uma que outro gestor ja decidiu) envia o formulario de aprovacao; a policy
  bloqueia o UPDATE, a solicitacao continua "pendente" no banco, mas a tela
  mostra "Acesso aprovado."/"Acesso negado." - a decisao nunca foi
  registrada, mas todos os envolvidos acreditam que foi. O mesmo padrao se
  repete ao cancelar solicitacao de outro usuario, resolver manutencao de
  hardware de terceiro, alternar publicacao de artigo sem ser autor/RH, etc.
  Como Server Actions do Next.js sao endpoints POST que continuam
  alcancaveis mesmo que o botao nao seja renderizado na tela do usuario
  (o RLS e a unica barreira real), qualquer usuario autenticado pode acionar
  essas actions diretamente e sempre recebe uma resposta de "sucesso".
Correcao sugerida:
  Encadear `.select("id")` apos o `.eq(...)` e checar se o array retornado
  esta vazio; se estiver, tratar como "nao encontrado ou sem permissao" e
  mostrar redirectWithError em vez de redirectWithSuccess.
Teste automatizado:
  test/unit/regression/update-sem-select-mascara-falha-de-permissao.test.ts
  (2 casos, ambos FALHAM hoje de proposito: aprovacao e cancelamento).


[V3] SEVERIDADE ALTA - Next.js desatualizado com ~20 CVEs conhecidas, sem patch na branch 14.x
Categoria: Vulnerabilidade de seguranca (dependencia)
Verificado via: npm audit (12/08/2026), next@14.2.35 instalado (ja e o ultimo
  patch disponivel em 14.2.x - npm nao encontrou versao 14.x que corrija os
  advisories; a correcao recomendada pelo proprio npm e upgrade major para
  next@16.3.0, "isSemVerMajor": true).
Descricao:
  A auditoria de dependencias aponta next.js (dependencia direta, producao)
  vulneravel a diversos CVEs publicados contra as faixas ">=13.0.0 <15.5.x"
  e ">=14.1.1 <15.5.21", entre eles (severidade HIGH):
  - SSRF em Server Actions (GHSA-89xv-2m56-2m9x) - MUITO relevante aqui, pois
    o projeto usa Server Actions extensivamente em todos os modulos.
  - SSRF em rewrites via hostname de destino controlado por atacante
    (GHSA-p9j2-gv94-2wf4).
  - Denial of Service em App Router usando Server Actions (GHSA-m99w-x7hq-7vfj).
  - Middleware/Proxy bypass em apps com i18n (GHSA-36qx-fr4f-26g5) - o
    middleware.ts deste projeto e a camada de UX que redireciona por role.
  - HTTP request deserialization causando DoS (GHSA-h25m-26qc-wcjf).
  Ha ainda diversos CVEs MODERATE de cache poisoning/cache confusion de
  Server Components e um de exposicao nao autenticada de endpoints internos
  de Server Function (GHSA-955p-x3mx-jcvp).
Correcao sugerida:
  Planejar upgrade do Next.js para a linha 15.5.21+ ou 16.x (major, com
  breaking changes esperados - nao e um "npm audit fix" trivial). Ate a
  migracao, considerar mitigacoes de borda (regras no Nginx/WAF planejado)
  para os vetores de SSRF/DoS mais criticos.
Observacao: eslint-config-next (devDependency) tambem reporta uma
  vulnerabilidade HIGH via glob (command injection, CWE-78) - impacto restrito
  ao ambiente de build/lint, nao ao runtime de producao.


[V4] SEVERIDADE ALTA - Bypass de "1 check-in de hardware por mes"
Categoria: Vulnerabilidade de seguranca / regra de negocio
Arquivo: supabase/migrations/0001_init.sql, linhas 272-289
Descricao:
  A constraint uq_checkin_asset_month (asset_id, reference_month) e uma
  UNIQUE real de banco (correto), mas a granularidade "por mes" depende
  inteiramente do backend truncar reference_month para o dia 1 antes do
  INSERT - nao ha CHECK garantindo
  "reference_month = date_trunc('month', reference_month)".
Cenario de exploracao:
  Uma chamada direta a API REST do PostgREST (contornando o Next.js) pode
  inserir reference_month = '2026-08-01', '2026-08-15' e '2026-08-31' para o
  mesmo ativo - tres check-ins "validos" no mesmo mes, pois a UNIQUE trata
  cada data como distinta.
Correcao sugerida:
  Adicionar `check (reference_month = date_trunc('month', reference_month)::date)`
  na tabela hardware_checkins.
Teste automatizado: test/unit/sql/migration-rls-static-checks.test.ts,
  caso "Achado SQL#2" (FALHA hoje de proposito).


[V5] SEVERIDADE MEDIA - signOutAction sem verificacao de origem (CSRF de logout forcado)
Categoria: Vulnerabilidade de seguranca (CSRF)
Arquivo: app/dashboard/actions.ts, linhas 6-10
Descricao:
  E a unica Server Action de todo o projeto que muda estado (auth.signOut())
  sem chamar assertTrustedOrigin() no inicio, ao contrario de absolutamente
  todas as outras actions de mutacao do codebase.
Cenario de exploracao:
  Um site malicioso pode montar um <form>/fetch cross-site apontando para
  esta action e forcar o logout de qualquer usuario autenticado que visite a
  pagina, sem interacao alem de abrir o link. Impacto limitado (incomodo/DoS
  de sessao, nao vazamento de dados), mas quebra o padrao de defesa em
  profundidade adotado no resto do app.
Correcao sugerida:
  Adicionar `await assertTrustedOrigin();` como primeira linha da funcao,
  igual as demais.
Teste automatizado: test/unit/regression/signout-sem-verificacao-de-origem.test.ts
  (FALHA hoje de proposito).


[V6] SEVERIDADE MEDIA - IP de auditoria confia em header repassavel pelo cliente
Categoria: Vulnerabilidade de seguranca (integridade de auditoria) / risco de
  deploy incompleto
Arquivos: lib/supabase/server.ts linhas 15-27, supabase/migrations/0001_init.sql
  linhas 667-687 (fn_audit_trigger, leitura de x-client-ip)
Descricao:
  O client_ip gravado em audit_logs vem do header HTTP customizado
  "x-client-ip", que o proprio Next.js (lib/supabase/server.ts) preenche a
  partir de "x-forwarded-for" da requisicao recebida. A garantia de que esse
  valor e confiavel depende 100% do Nginx, em producao, sobrescrever (nao
  concatenar) X-Forwarded-For com $remote_addr antes de repassar ao Next.js -
  o que esta corretamente documentado e configurado em
  ARQUITETURA_TECNICA.md (secao 6.2), mas o deploy em EC2/Nginx ainda esta
  marcado como "Pendente" no README.md (linha 100: "Deploy AWS EC2 - Pendente").
Cenario de exploracao:
  Em qualquer ambiente onde o Next.js seja acessado sem esse Nginx especifico
  na frente (ambiente de dev/staging exposto por engano, deploy alternativo,
  ou uma futura reconfiguracao de proxy que nao preserve exatamente
  "set_real_ip_from"/"real_ip_header"), um usuario autenticado pode forjar
  livremente o header X-Forwarded-For e ter qualquer IP de sua escolha
  gravado como autor (client_ip) de suas proprias acoes na trilha de
  auditoria - uma trilha que a documentacao do projeto trata como prova
  forense de "quem fez o que, quando".
Correcao sugerida:
  Nao ha correcao de codigo pendente (a decisao de design esta documentada e
  e razoavel dentro da topologia planejada) - o item fica registrado para
  garantir que, no momento do deploy, o Nginx com "set_real_ip_from" seja
  validado antes de a aplicacao ir ao ar, e para que nenhum ambiente
  intermediario (dev/staging) fique acessivel publicamente sem essa camada.


[V7] SEVERIDADE MEDIA - CASCADE em contratos e check-ins ao excluir um ativo de hardware
Categoria: Instabilidade / risco de perda de auditoria
Arquivo: supabase/migrations/0001_init.sql, linhas 263-270 e 275-289
Descricao:
  hardware_status ja modela retirada de circulacao via 'baixado'/'extraviado'
  (nunca deveria ser necessario excluir um ativo de fato), mas
  hardware_contracts.asset_id e hardware_checkins.asset_id usam
  "on delete cascade". admin_ti tem CRUD completo sobre hardware_assets
  (policy "for all"). Um DELETE em um ativo (acidental ou por um admin
  comprometido) apaga silenciosamente os contratos assinados e todo o
  historico de check-ins associados - dados que o proprio schema trata como
  registro que "nunca deve ser apagado" para colunas analogas
  (requester_id/profile_id continuam RESTRICT).
Correcao sugerida:
  Trocar para "on delete restrict" nessas duas FKs, forcando o uso do campo
  status para retirar um ativo de circulacao em vez de exclui-lo.
Teste automatizado: test/unit/sql/migration-rls-static-checks.test.ts,
  caso "Achado SQL#4" (FALHA hoje de proposito).


[V8] SEVERIDADE MEDIA - Actions administrativas sem checagem explicita de role no app
Categoria: Vulnerabilidade de seguranca (defesa em profundidade ausente)
Arquivos: admin/catalogo/actions.ts, admin/hardware/actions.ts,
  admin/telefonia/actions.ts, wiki/actions.ts (createCategoryAction)
Descricao:
  Nenhuma dessas actions chama supabase.auth.getUser() ou verifica o role do
  usuario antes de tentar a mutacao - dependem 100% do RLS. Isoladamente,
  isso e relativamente seguro para INSERT (a policy WITH CHECK bloqueia e o
  erro e logado com mensagem generica ao usuario). O problema real e a
  combinacao com o achado V2: nas mesmas actions que fazem UPDATE/toggle
  (toggleCatalogItemActiveAction, updateHardwareAssetStatusAction,
  updateMobileLineAction), a ausencia de checagem no app remove a unica
  chance de dar uma mensagem clara ("sem permissao") em vez de depender do
  efeito colateral silencioso descrito em V2.
Correcao sugerida:
  Adicionar uma checagem leve de profiles.role no inicio dessas actions,
  mesmo que redundante com o RLS, para produzir mensagens de erro corretas.


[V9] SEVERIDADE BAIXA - Upload de foto de check-in confia no Content-Type declarado pelo cliente
Categoria: Vulnerabilidade de seguranca (validacao incompleta)
Arquivo: app/dashboard/hardware/actions.ts, linhas 38-44, 73, 81
Descricao:
  file.type vem do metadata do File/Blob enviado pelo cliente (facilmente
  falsificavel). A validacao server-side compara essa string contra uma
  allowlist e depois a reutiliza como contentType do objeto salvo no
  Storage - sem verificacao de assinatura binaria (magic bytes). O upload de
  contrato (admin/hardware/actions.ts:122), em contraste, usa um contentType
  fixo "application/pdf" independente do que o cliente informou - um padrao
  mais seguro que poderia ser replicado aqui.
Correcao sugerida:
  Validar a assinatura binaria real do arquivo no servidor antes do upload,
  em vez de confiar apenas no header MIME informado pelo cliente.


[V10] SEVERIDADE BAIXA - IDs validados manualmente em vez de via Zod .uuid()
Categoria: Instabilidade / inconsistencia
Arquivos: admin/catalogo/actions.ts:53-58, admin/hardware/checkins/actions.ts:15-20,
  wiki/actions.ts:86-89 e 129-134
Descricao:
  Ao contrario do resto do codigo (Zod .strict() + .safeParse sistematico),
  essas quatro actions validam o id manualmente com
  "typeof id !== 'string' || id.length === 0", sem checar formato UUID. Um
  valor nao-UUID chega ao .eq(...) e o Postgres rejeita com erro de sintaxe
  de tipo (capturado e traduzido em mensagem generica - sem leak, mas
  inconsistente com o padrao do restante do projeto).
Correcao sugerida: aplicar z.string().uuid() tambem nesses pontos.


[V11] SEVERIDADE BAIXA - Aplicacao nao emite CSP/HSTS proprios
Categoria: Instabilidade de configuracao (defesa em profundidade)
Arquivo: next.config.mjs, linhas 4-9
Descricao:
  O README.md e o ARCH_DECISIONS.txt afirmam que "a aplicacao deve emitir
  CSP restritivo, HSTS e X-Frame-Options por padrao". Na pratica,
  next.config.mjs emite apenas X-Frame-Options, X-Content-Type-Options,
  Referrer-Policy e Permissions-Policy - Content-Security-Policy e
  Strict-Transport-Security sao emitidos apenas pelo Nginx (documentado em
  ARQUITETURA_TECNICA.md, secao 6.2), que ainda nao foi implantado (deploy
  "Pendente"). Ate o deploy, qualquer acesso direto a aplicacao (ex.:
  ambiente de desenvolvimento exposto, ou uma instancia acessada sem passar
  pelo Nginx) fica sem CSP/HSTS.
Correcao sugerida:
  Duplicar ao menos um CSP restritivo (mesmo que redundante com o Nginx) em
  next.config.mjs, como e feito com os outros quatro headers, para que a
  aplicacao nao dependa de uma unica camada para essa proteção.


[V12] SEVERIDADE BAIXA - "ON DELETE" inconsistente entre FKs de atribuicao/autoria
Categoria: Instabilidade (integridade referencial)
Arquivo: supabase/migrations/0001_init.sql, linhas 253 (hardware_assets.assigned_to),
  305 (mobile_lines.assigned_to), 328-329 (created_by/updated_by de artigos),
  325 (category_id de artigos), 346 (audit_logs.changed_by)
Descricao:
  O proprio arquivo documenta (linhas 77-82) que profiles.manager_id foi
  corrigido para "on delete set null" para nao bloquear a exclusao
  definitiva de um usuario em auth.users (ex.: LGPD). O mesmo raciocinio nao
  foi replicado nas FKs acima, todas sem clausula "on delete" (= RESTRICT
  implicito): excluir um colaborador com hardware/linha atribuida, ou um
  autor de artigo da wiki, ou qualquer usuario que ja tenha uma linha em
  audit_logs (ou seja, praticamente todos), falha com erro de integridade
  referencial.
Correcao sugerida:
  Aplicar "on delete set null" de forma consistente nessas colunas (ou
  adotar explicitamente anonimizacao de perfil em vez de hard delete de
  auth.users, documentando a excecao).
Teste automatizado: test/unit/sql/migration-rls-static-checks.test.ts,
  casos "Achado SQL#3a/3b/3c/5" (FALHAM hoje de proposito).


[V13] SEVERIDADE BAIXA - Cobertura de auditoria incompleta
Categoria: Instabilidade (rastreabilidade)
Arquivo: supabase/migrations/0001_init.sql, linhas 709-742

ACHADOS NAO CORRIGIDOS NESTA RODADA (decisao registrada - exigem decisao de
produto/escopo maior antes de virar codigo)
------------------------------------------------------------------------------
- Paginacao/N+1: praticamente todas as paginas de listagem (relatorios,
  inventario de hardware, telefonia, catalogo, aprovacoes, wiki) buscam
  todas as linhas sem paginacao; os somatorios financeiros do Dashboard
  Executivo sao calculados em JavaScript depois de baixar todas as linhas em
  vez de agregacao SQL; e duas paginas fazem createSignedUrl em loop
  sequencial por linha (sem Promise.all). Nao dói com o volume de dados
  atual (ambiente de teste praticamente vazio), mas e uma bomba-relogio de
  performance/DoS de app em producao com volume real.
- is_manager_of(target_id) e uma function RPC executavel por qualquer
  usuario autenticado com qualquer target_id (GRANT EXECUTE necessario para
  a RLS poder chama-la) - funciona como oraculo de organograma (sondar "sou
  eu o gestor deste ID?" para ids arbitrarios). Nao e escalonamento de
  privilegio, mas e exposicao maior que is_admin()/current_role(), que so
  revelam dado do proprio chamador.
- hardware_contracts permite DELETE via policy "for all" para admin_ti,
  enquanto hardware_checkins deliberadamente nao tem NENHUMA policy de
  DELETE - inconsistencia entre duas tabelas que o proprio schema descreve
  como registro historico "que nunca deveria ser apagado". Precisa de
  decisao de produto sobre se contratos assinados podem mesmo ser excluidos.
- hardware_checkins_insert verifica so assigned_to = auth.uid(), sem checar
  hardware_assets.status - um check-in pode ser aberto para um ativo ja
  baixado/extraviado/em_manutencao. Pode ser intencional, mas nao ha decisao
  explicita registrada em codigo/comentario.
